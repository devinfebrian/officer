# Workflow
- Prefers to handle git commit and push themselves rather than delegating version control to the agent — after finishing a feature they commit/push on their own and expect the agent to proceed to the next task (e.g., "i already commit and push, plan s2"). Confidence: 0.7
- Prefers test-first TDD in small vertical slices: write the failing test, confirm it's red, implement just enough to go green, then move to the next seam — each slice pairs one test with one implementation unit. When a newly written test fails and contradicts the intended semantics, the test is fixed rather than the code. Confidence: 0.9
- Prefers empirically probing framework/library behavior with a throwaway scratchpad script before committing to a design or wiring decision (e.g., confirming LangGraph conditional-edge routing and dict-merge semantics before rewriting the orchestrator). Confidence: 0.8
- User's environment is Windows (cmd shell): Unix-only shell tools like `tail` aren't available — keep shell commands plain instead of piping to text tools; `%VAR%` expansion, `NUL`, and `2>&1` redirection work. Confidence: 0.9
- Wants a real-browser visual verification pass for frontend/UI work, and is willing to install recommended tooling to enable it — installed agent-browser on the agent's request specifically so it could screenshot and interact with the dashboard ("i have installed agent-browser can you check?"). agent-browser (v0.35.1, npm CLI) is now available in the environment: open/screenshot/eval/wait/network/console, isolated sessions via `--session <name>`. Confidence: 0.8
- Likes to verify finished work by hand, not just via the agent's automated tests — asks for manual testing instructions at handoff ("how can i test this manually?"). When delivering a feature, include the exact run/start command, the URL to open, and a checklist of behaviors to poke (happy path, error paths, and edge cases like mid-run refresh and multi-tab sync). Confidence: 0.5
- Handles secrets carefully during debugging: when inspecting `.env`/env config, print variable names only and never echo values into terminal output or logs (the `.env` loader shipped with a "No value is ever logged" contract). Confidence: 0.7
- Prefers minimal stdlib implementations over adding new dependencies for small needs — wrote a small stdlib `.env` loader (real env wins over file, missing file silently ignored) instead of installing python-dotenv. Confidence: 0.6
- Wants fixes proven with a real end-to-end run against the actual external service before declaring done ("the real proof — a run against the actual Gemini API with your .env key"), since fake-backed unit tests masked real bugs; use throwaway/temp databases during such verification so the user's real demo data (audit trail) stays clean. Confidence: 0.7
- Preserves the user's concurrent manual edits when applying changes: re-read the file and build on its current content rather than overwriting (kept the user's mid-session model switch to `gemini-3.5-flash` while applying the fix). Confidence: 0.6
